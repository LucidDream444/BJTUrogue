## 二、为什么网站式更好

| 维度 | 桌面客户端 | 网站式 |
|---|---|---|
| **反馈收集摩擦** | 要下载安装包，测试者流失严重 | **一个 URL 点开就玩**，反馈按钮调同域 API |
| **版本更新** | 每次出包都要重新分发 | **刷新即最新版**，玩家自动拿到 |
| **部署** | 分发安装包 / 网盘 / 杀软误报 | 静态文件，扔到服务器即可 |
| **跨平台** | 需分别出 Windows / Mac 包 | 任意设备有浏览器就能玩 |
| **同域 API** | 需处理跨域与网络配置 | 与后台同域，**无跨域问题** |
| **版本回退（UC11）** | 需重新分发旧包 | **切换静态目录即可**，回退瞬间完成 |
| **协作冲突** | 全文本，无冲突 | 全文本，无冲突 |

**这直接改善了你们需求文档里的几个点：**

- §1.1「本地离线」→ 用 Service Worker 做离线缓存，首次加载后断网可玩，**定位依然成立**
- UC07 反馈流程 → 从"导出反馈包自行交给项目组"变为"填完直接提交"，且可保留导出功能
- UC11 版本发布与回退 → 静态资源按版本号分目录，回退 = 切换目录

## 三、客户端：Phaser 3 + TypeScript

### 为什么是 Phaser

**上一版（pygame）最大的风险是"手感全部要自研"。Phaser 把这一半的工作直接消掉了：**

| 手感要素 | pygame 方案 | Phaser 3 |
|---|---|---|
| 震屏 | 自研摄像机偏移 + 衰减 | `camera.shake()` ✅ |
| 闪白 / 闪光 | 自研色值叠加 | `camera.flash()` ✅ |
| 缓动 / 补间 | 自研缓动函数库 | `tweens.add()` ✅ |
| 粒子 | 自研粒子池 | `add.particles()` ✅ |
| 精灵动画 | 自研切帧系统 | `anims.create()` ✅ |
| 碰撞检测 | 自研 AABB | Arcade Physics ✅ |
| 地图 | 自研 | Tiled 导入 ✅ |
| 场景管理 | 自研 | Scene 系统 ✅ |
| 时间缩放（暂停） | 自研 | `time.timeScale` ✅ |
| 输入 | 自研映射 | `Phaser.Input`（键鼠 + 手柄）✅ |

**仍要自己做的**：顿帧（Hitstop，用 `timeScale` 几行即可）、输入缓冲、固定时间步、屏幕后效。工作量比 pygame 方案小一个量级。

其他收益：社区庞大（roguelike 教程极多）、TypeScript 类型系统让**接口契约可以类型化**（C1/C2/C3 都能落成 `.d.ts`，编译期就能发现契约不一致）、Vite 热重载让迭代以秒计。

### 依赖

```json
{
  "dependencies": { "phaser": "^3" },
  "devDependencies": {
    "typescript", "vite",
    "vitest",              // 逻辑单测
    "eslint", "prettier"
  }
}
```

**刻意不引入**：状态管理库（Redux 等）、ECS 框架、UI 组件库。Phaser 的 Scene 与 GameObject 已经够用，额外抽象只会增加五人的沟通成本。

## 四、客户端架构

```
src/
├── core/                    共用层（改动需全员同意）
│   ├── events.ts            事件总线  ← C1 契约的落地形态
│   ├── config.ts            配置加载 + 类型定义（由 JSON Schema 生成）
│   ├── rng.ts               确定性随机（种子可复现，对应文档 R03）
│   ├── time.ts              统一时间缩放包装
│   └── assets.ts            资源清单与加载
│
├── domains/                 各域独立目录，文件级所有权
│   ├── combat/      D1      战斗 Scene、武器、奖励、手感实现
│   ├── procgen/     D2      生成器、可达性校验、房间构建
│   ├── enemies/     D3      敌人 AI、寻路、行为配置
│   └── meta/        D4      主菜单、结算、升级页、存档、设置
│
└── main.ts
```

### 并行分工的机制

1. **Scene 是天然模块边界。** 每个域拥有自己的 Scene（战斗、主菜单、结算、升级页），互不修改对方的 Scene。
2. **事件总线是唯一的跨域通道。** 不直接调用对方的方法。
3. **组件式扩展而非完整 ECS。** Phaser 的 GameObject 模型不适合硬上 ECS；采用「GameObject + 自定义数据组件 + 事件总线」，同样能让 D1 与 D3 各自加行为而不改对方代码，且学习成本低得多。
4. **配置类型化。** 所有读配置的代码都有 `.d.ts` 类型，D2 改字段时 D1/D3 会在编译期报错——契约不一致在写代码时就暴露，不用等运行时。

### 事件总线（C1 契约）

```typescript
// core/events.ts
Bus.emit('room_cleared', { roomId, seed, clearTime });
Bus.emit('entity_damaged', { targetId, amount, sourceId, isCrit });
Bus.emit('run_ended', { result: 'win' | 'dead', depth, unlocks });
```

订阅方：D1（HUD）、D3（敌人表现）、D4（结算界面）、D5（遥测上报）。
**D5 的遥测只需订阅事件总线，完全不碰战斗代码。**

## 五、配置数据管线（D2 的核心产出）

```
CSV / Google Sheets              ← 唯一数据源，进 git，可 diff 可合并
        ↓
Python 校验脚本（pydantic）       ← D2 编写，D5 复用同一份模型校验 API 入参
   字段类型 / 数值范围 / 枚举合法性
   资源引用存在性
   地图可达性（1000 随机种子，接入 CI）
        ↓
JSON（产物） + JSON Schema
        ↓
json-schema-to-typescript        ← 生成 .d.ts
        ↓
D1 / D3 以类型安全方式读取
```

**规则：任何数值不得写死在 TypeScript 代码里。** 迭代 3 要调的数值量极大，写死等于每改一次平衡就重新构建。

**一个额外收益**：pydantic 模型客户端与服务端共用，**D2 与 D5 之间有共同语言**。

## 六、服务端：Django 5 + DRF + Django Admin

游戏是 TypeScript，服务端仍推荐 Python/Django，理由是**后台的绝大部分是白拿的**：

| 需求（文档对应） | Django 提供 | 自己写的量 |
|---|---|---|
| 管理后台界面（S2） | **Django Admin** 开箱即用 | 仅定制 `list_display` / `list_filter` / `actions` |
| 账号管理：封禁 / 重置（S5） | Admin 内置用户管理 | 近零 |
| 三类维护角色权限（S5，对应 §2.1） | Admin 的 Groups + Permissions | 建 3 个 Group |
| 审计日志（S5） | **`LogEntry`** 自动记录所有增删改 | 近零 |
| 反馈工单看板（S2 / S3） | Admin 列表 + 自定义 filter + 状态流转 action | 一个 ModelAdmin |
| REST API（C3 契约） | DRF + `drf-spectacular` 自动生成 OpenAPI | 几个 ViewSet |
| 数据库迁移（迭代 3 加账号字段） | Django migrations | `makemigrations` |

**S5 阶段"三角色权限 + 账号管理 + 审计日志"几乎零开发量。**

> **备选：全栈 TypeScript**（Phaser + NestJS + React-Admin）。
> 好处是一个语言、D5 与其他域完全互通；代价是后台 CRUD、RBAC、审计日志全部要自己写，D5 工作量显著上升。
> **仅当 D5 明确更熟 Node 且愿意承担这份工作量时才改选。** 默认方案保留 Django。

### 匿名 ID 模型（"最小 MVP 无账号"的关键）

```python
class Player(models.Model):
    anon_id = models.UUIDField(unique=True, db_index=True)   # 客户端首次启动生成
    user = models.OneToOneField(User, null=True, blank=True,
                                on_delete=models.SET_NULL)    # S4 账号上线后绑定
    created_at = models.DateTimeField(auto_now_add=True)
```

- S1 起：客户端带 `anon_id` 提交反馈，服务端建立"匿名档案"
- S4 账号上线：`claim(anon_id, user)` 绑定，历史反馈自动继承
- **S1 到 S6 都不需要改这个模型的结构**——每个阶段不推翻前一个阶段

## 七、部署

```
一台云服务器
└── Docker Compose
    ├── caddy      反向代理 + 自动 HTTPS（配置三行）
    ├── web        Django + gunicorn
    └── db         PostgreSQL 16（数据卷持久化）

Caddy 同时服务静态文件：
    /game/v1.2.3/   ← 客户端构建产物，按版本号分目录
    /game/current/  ← 指向当前版本的软链接
```

**游戏与后台同域**：玩家打开 `https://xxx/game` 直接玩，反馈按钮调同域 API，**无跨域配置**。

**版本回退（对应 UC11）**：静态产物按版本号分目录，回退 = 把 `current` 指向旧目录，**瞬间完成且不影响数据库**。这比桌面版重新分发旧包干净得多，是网页方案的一个额外加分项。

其他：`pg_dump` 定时备份保留 7 份；反馈附件挂本地数据卷由 Caddy 静态服务；**不要搞 staging / k8s**。

## 八、浏览器特有的工程问题

**这一节是网页方案独有、桌面方案没有的坑。必须在第 5 周前知悉，否则会以"玄学 bug"的形式反复出现。**

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| 1 | **切标签页时 `requestAnimationFrame` 停止** | 切回来时单帧 delta 可能是几十秒，角色瞬移穿墙 | **必须钳制 delta**（每帧上限 1/30 秒）。最常见的一个 bug |
| 2 | **F5 刷新 = 本局进度全丢** | 与 P0 需求"暂停/继续、退出需确认进度丢失"冲突 | `beforeunload` 拦截 + 局内状态存 `sessionStorage` |
| 3 | **音频自动播放限制** | 首次进入无声音 | 主菜单需要一次用户点击才能解锁音频（所有浏览器通用限制） |
| 4 | **全屏 / 指针锁定需用户手势** | 不能在加载时自动全屏 | 全屏请求必须写在点击事件处理函数内 |
| 5 | **高 DPI 屏模糊** | 画面发虚 | 处理 `devicePixelRatio`，Phaser 的 `resolution` 与缩放模式要配对设置 |
| 6 | **首屏加载时间** | 加载慢会让测试者直接关掉 | 资源压缩 + 加载进度条 + 按场景分包加载；**音频素材体积严格控制** |
| 7 | **断网不可玩** | 与 §1.1「本地离线」定位冲突 | Service Worker 缓存，首次加载后离线可玩 |
| 8 | **遥测在离线时丢失** | 反馈数据缺失 | 反馈与遥测**写入本地队列**，联网后自动补传（与匿名 ID 机制天然配套） |

> 第 1 条和第 8 条是最容易忽略、代价最大的两条。前者产生难以复现的"穿墙"缺陷，后者让服务端收集到的数据不完整。

## 九、排除项及理由

| 不选 | 理由 |
|---|---|
| Unity / Godot / UE / Cocos | 按团队要求排除；且引擎场景文件冲突对五人协作是持续成本 |
| **pygame-ce + pygbag** | 能保住全栈 Python 与 Django 优势，但 WASM 有实打实的代价：首屏要下载数 MB 的 Python 运行时、加载慢、性能受限、pygbag 工具链不成熟。**手感还要全部自研**。网页方案里 Phaser 明显更优 |
| **原生 Canvas / PixiJS** | 前者太底层，后者只是渲染库，手感工具（震屏、补间、粒子）都要自己补，等于退回 pygame 方案的问题 |
| **Godot Web 导出** | 属引擎，已排除；且 Web 导出包体大 |
| **LibGDX / Java** | 样板代码多，GWT 导出 Web 麻烦 |
| **Rust + Bevy / wasm** | 学习曲线与构建链复杂度对本项目周期风险过大 |
| **全栈 TypeScript + NestJS** | 可行，但会丢掉 Django Admin 免费提供的后台、RBAC、审计日志，D5 工作量显著上升。**列为备选而非默认** |
| **微服务 / Redis / 消息队列 / k8s / Nginx** | 五人课程项目，纯属自找复杂度；Caddy 更省事 |

## 十、与分工的对应

| 域 | 技术栈 |
|---|---|
| D1 战斗核心 | Phaser 3 + TypeScript + 事件总线 + 手感实现 |
| D2 关卡与配置管线 | TypeScript（生成器）+ Python + pydantic（校验脚本） |
| D3 敌人与首领 | Phaser 3 + TypeScript（AI 与寻路）+ Vitest |
| D4 局外成长与存档 | Phaser Scene + TypeScript + localStorage / 服务端 |

## 十一、风险与缓解

### R-T1：浏览器性能上限

**缓解**：本项目定位"轻量化"、2D 俯视角、同屏实体数百量级，Phaser 完全够用。真遇瓶颈时按顺序处理：① 减少每帧对象创建（对象池）；② 限制同屏粒子上限；③ 关闭不必要的物理体。**不要在早期做性能优化，先出可玩版本。**

### R-T2：D1 的手感实现仍有自研部分

Phaser 消掉了大部分，但**顿帧、输入缓冲、固定时间步**仍需自研。

**缓解**：这三项合计不超过两天工作量。**第 5 周的 MVP 里程碑必须包含它们**，排在功能开发之前——它们缺了，"战斗爽快感"（需求文档第一优先级）就无从谈起。

### R-T3：浏览器特有的"玄学 bug"

第八节的 8 个问题都是真实且高频的。

**缓解**：**把它们写进第 5 周前的技术预研清单**，每一条都用最小 demo 验证一遍，不要等到迭代 2 才发现。其中"delta 钳制"和"音频解锁"两条，如果第 5 周没做对，后面要改主循环和主菜单结构。

### R-T4：D5 的打包与部署职责偏重

D5 同时管服务端、后台、构建、部署、版本回退。

**缓解**：**客户端构建与部署流水线在迭代 1 内打通**，不要拖到迭代 3。之后每次发布都应是一行命令，纳入 CI 自动执行。静态目录的版本化方案（第七节）要在迭代 1 就定下来，它同时是 UC11 的落地方式。

## 十二、版本与依赖锁定

| 项 | 版本 | 备注 |
|---|---|---|
| Node.js | **20 LTS** | 全员一致，写入 `.nvmrc` |
| TypeScript | 5.x | |
| Phaser | 3.x 最新稳定版 | 锁定小版本 |
| Vite | 5.x | |
| Python | **3.12** | 服务端；写入 `requires-python` |
| Django | 5.x | |
| PostgreSQL | 16 | Docker 镜像固定小版本 |
| Docker Compose | v2 | |

**规则：依赖一律写进 `package.json` / `pyproject.toml` 并锁定版本。** 全文本方案的协作成本虽低，但依赖漂移会导致"我这能跑"的排查成本。
