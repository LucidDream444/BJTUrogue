## 摘要

单局地图是**教学楼的一层**：一**排**主干教室横着排开，相邻两间之间由一小段**连廊**相连
（**没有贯穿全层的走廊**），侧室随机挂在某几间主干教室的上方或下方。
**一局固定 15 间房**（主干 8—11 间 + 侧室 15 − 主干 间），房间按 `order` 串成一条
**进度轴**，最后一间恒为首领。教室内部随机摆课桌与椅子（**只横竖、按格对齐**），课桌挡路也挡子弹，
椅子挡路不挡子弹。全部数值在 `client/public/config/rooms.json`，改数值不需要重新构建。

三个消费方各自只关心一件事：

| 谁 | 从哪儿接手 | 别碰什么 |
|---|---|---|
| **D1** 战斗 | `map.walls` 建碰撞体、`room.doors` 决定哪扇门在战斗期间封上、`room.obstacles` 决定课桌/椅子的子弹分组 | 不要自己从 `rooms` 反推墙 —— 见 §2.5 |
| **D3** 敌人 | `buildWalkability(map)` 注入 `FlowField`，`room.spawnPoints` 是刷怪位置 | 不要自己算格子 —— `navCellSize` 与 `navOrigin` 在数据里 |
| 双方 | `room.order` 是**顺序的唯一来源** | 不要用坐标推「谁在谁后面」 |

# 一、这层楼长什么样

## 1. 平面结构

```
                      ┌───────────┐                        ┌───────────┐
   北侧                │  侧室 #2  │                        │  侧室 #9  │   ← 随机挂上方或下方
                 ┌─────┴───┬───────┴──────┐          ┌────┴─────┬──────┴────┐
                 │         │              │          │          │           │
   主干一排       │  #0     │连廊 │  #1     │   …      │  #3      │连廊 │ #4   │ …  │ #14 首领 │
                 │  起点   │     │  主干   │          │  主干    │     │ 主干 │
                 └─────────┴─────┴────────┘          └──────────┴─────┴──────┘
                              ↑ 连廊夹在相邻两间之间，共「主干数 − 1」段

   侧室的西边界落在**宿主的东段**里，东边界接在**连廊的东端** —— 它横跨
   「宿主的一部分 + 一整段连廊」，朝主干那面墙上开两扇门（一扇进宿主、一扇进连廊）。
```

（示意图，不是比例图。真图看测试场 `d2_floorplan`，见 §7.2）

- **没有贯穿全层的走廊。** 主干教室是主体，一间挨着一间横着排开；相邻两间之间只夹着
  一小段**连廊**（§1.3 有尺寸）。玩家看到的是一排教室，不是一条长走廊配两排配菜。
- **主干教室与连廊在同一条水平带里交替排开**，于是「教室的上下两面墙」与「连廊的上下两面墙」
  是**同两条直线**。这一条是侧室那面墙能一次贴合住宿主与连廊的前提（见下一条）。
- **侧室的挂靠侧（上／下）由种子随机定**，不是按宿主序号交替 —— 「随机刷新」在这排房子上的
  表现就是「哪几间挂了侧室、挂在上还是下、房间多宽」全都随种子变。
- **侧室的出口进连廊**（→ 汇回主干道**下一间**），不是回到宿主里。所以「进不进侧室」
  不改变必经路径的终点。它的入口来自宿主那一间。
- **`roomGap` 是连廊沿 x 的长度**（不是「两间房之间让出来的空隙」）。名字没改、语义换了，
  v1.0 写下的消费方注意这一点。

## 2. 进度轴（`order`）

`order` 从 0 起**连续无洞**，按「主干第 i 间 → 挂在它上面的侧室 → 主干第 i+1 间」交错编号。
这么编的直接好处：**`order` 的升序正好等于平面上的从左到右**，缩略图上的顺序就是进度顺序，
不需要第二张表去对照。

三条顺序相关的不变量（校验器会拒）：`rooms[0].kind === 'start'`、**主干轴最后一间的
`kind === 'boss'`**、`budget` 沿主干轴单调不减。

> ⚠️ **「最后一间」指的是主干轴最后一间，不是 `rooms[14]`。** 首领后面不可能挂侧室
> （它的出口要「汇回下一间」，而它后面没有下一间），所以这两者在当前生成器里恰好相等 ——
> 但**判定请写成「主干轴最后一间」**，别写成 `rooms[rooms.length - 1]`。

## 3. 连廊的实际尺寸（D3 直接用到）

以当前 `rooms.json` 为准。**主干教室与连廊等高**，所以下面这一组数对两者都成立：

| 量 | 值 | 怎么来的 |
|---|---|---|
| `Passage.rect.height` | **280px** | = `mainRoomHeight`，与主干教室同高 |
| 上下两条外墙的中心线 | `y = ±140` | `mainRoomHeight / 2` |
| **连廊实测净宽** | **240px = 6 格** | 由网格量出来（`checkReachability().passageClearWidths`），不是照配置抄的 |
| `Passage.rect.width` | **200px** | = `roomGap`（含两端各半堵墙，见下） |
| 连廊内部沿 x 的净长 | **160px = 4 格** | `roomGap − wallThickness` |
| 全层**最窄窄口** | **120px = 3 格** | `checkReachability().narrowestOpeningWidth` = 连廊净宽与**每一扇门宽**取小 |
| 配置下限 | 120px | `minPassageWidth`；校验器断言「实测窄口 ≥ 下限」 |

> **`Passage.rect` 是含墙的**（和 v1.0 的 `corridorRect` 同约定）。墙**骑在它的上下两条边上**
> 画（各 40px 厚，往里外各吃 20px），所以可走的是**里面**那 240px —— `280 − 40`，
> **不是 `280 − 80`**。拿 `rect.height` 当可走宽度会**多算 40px（一格）**，
> 而且这个错**不会报任何错**：面板上多个数，只有走到连廊边上才会发现过不去。
> （v1.0 就在这个减法上被两个测试场读出两个数 —— 所以现在两边都走
> `config.passageClearWidth(cfg)` 这一个函数。）

**连廊不做窄喉**（已定）：它保持 240 净宽，**门（120）才是全层唯一的窄口**。
「门就是那一个卡点」比「连廊里还要再卡一次」好读，也好让玩家自己判断值不值得绕侧室。

为什么连廊净宽是 240 而不是配置下限的 120：`minPassageWidth` 是**下限**，
构造比它宽不会失败。240px 对肉盾（直径 80）留了三倍余量，是有意的余地。

**每一段连廊都是 `N − 1` 段之一**（`N` = 主干教室数），两端各有一扇竖直的门。
`Passage.between` 报出它连接的两间主干教室的 `order`（升序）——
D1 的封门与「不回头」逻辑靠它，不必靠坐标去猜这一段接的是谁。

## 4. `branch` 与 `kind` 是**两个**正交字段

| 字段 | 回答 | 取值 |
|---|---|---|
| `branch` | 在**主干上还是侧室** | `'main'` / `'side'` |
| `kind` | 里面**装的是什么** | 7 类内容类型 |

7 类一次定完：`start` / `main` / `elite` / `reward` / `shop` / `boss` / `hidden`。
**本期生成器只产出 `start` / `main` / `boss`**，其余四类留给迭代 2；校验器**接受全部 7 类**。

> ⚠️ **没有 `mandatory` 字段。** 「这间必须清图才能前进」是 `branch === 'main'` 的结论，
> 不是原生事实 —— 存一份就是两个真值来源。
>
> ⚠️ **侧室当前的 `kind` 是 `'main'`**（本期侧室里装的就是普通教室）。读 `kind` 判断
> 「要不要清图」会得到错的答案 —— **要判断必不必经，读 `branch`**。迭代 2 给侧室
> 安排内容时才会改成 `elite` / `reward` / `shop`。

# 二、字段表

全部定义在 `client/src/domains/procgen/model/types.ts`。**纯数据，零 Phaser 依赖。**

## 1. `DungeonMap`

| 字段 | 类型 | 说明 |
|---|---|---|
| `schemaVersion` | `number` | 当前 **`2`**（v1.0 是 `1`）。**红线 3**：缺了校验器直接报错，对不上也报错 |
| `seed` | `number` | 这次的种子。复现的钥匙 |
| `bounds` | `Rect` | 整层包围盒（**取所有墙的外侧面**，含墙厚）。缩略图与相机取景依据 |
| `passages` | `readonly Passage[]` | **主干教室之间的连廊**，按 x 从左到右，共「主干数 − 1」段。**含墙**，见 §1.3 |
| `walls` | `readonly Rect[]` | **每一段墙**。上下两条连续墙线（只在侧室门处断开）+ 房间之间的竖直隔墙 + 侧室另外三面，全在这儿 |
| `rooms` | `readonly Room[]` | 全部房间，**按 `order` 升序** |
| `navCellSize` | `number` | 寻路格边长。当前 `40` |
| `navOrigin` | `Point` | 网格的**最小角**（不是格子中心偏移！） |
| `elapsedMs` | `number` | 生成耗时。**仅供观测**，不参与任何判定 |

### 1.1 `Passage` —— 一段连廊

| 字段 | 类型 | 说明 |
|---|---|---|
| `rect` | `Rect` | 连廊矩形。**含上下两道墙**，可走的是里面那条，见 §1.3 |
| `between` | `[number, number]` | 它连接的两间主干教室的 `order`（**升序**） |

**连廊不是 `Room`**：不计入房间总数、没有 `order`、没有预算、不刷怪、不参与清房判定。
玩家在连廊里**永远处于脱离战斗的状态**。`rooms.length` 与 `passages.length` 是两个数
（15 间房、但只有「主干数 − 1」段连廊）。

## 2. `Room`

| 字段 | 类型 | 说明 |
|---|---|---|
| `order` | `number` | 进度轴位置，从 0 起连续无洞。**顺序的唯一来源** |
| `kind` | `RoomKind` | 7 类内容类型，本期产出 `start` / `main` / `boss` |
| `branch` | `RoomBranch` | `'main'` 必经 / `'side'` 可选 |
| `rect` | `Rect` | 房间矩形。**`x` / `y` 是中心点**，见 §2.6 |
| `sizeTier` | `number` | 用了几号档位。**索引到哪张表由 `branch` 决定**：主干 → `mainWidthTiers`（只按宽度分档）、侧室 → `sideRoomTiers`。校验器会拿尺寸反查并比对 |
| `doors` | `readonly Door[]` | 这间房的门。当前生成器保证**每间至少 1 扇**（起点只有 forward、首领只有 back、侧室有 2 扇），但别把「一定 ≥ 1」当成契约写进产品代码 |
| `obstacles` | `readonly Obstacle[]` | 课桌与椅子 |
| `spawnPoints` | `readonly Point[]` | 刷怪点。**每一个都从门可达** —— 由构造保证，不是校验出来的 |
| `budget` | `number` | 威胁预算。**与难度档位无关**；难度只乘在「预算 → 具体刷怪」那一步 |
| `anchoredTo` | `number \| null` | 侧室挂在主干第几间（`order` 值）。主干房间恒为 `null` |

## 3. `Door` —— 也就是墙上的**一段缺口**

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | `'back' \| 'forward' \| 'side'` | 见下表 |
| `x` / `y` | `number` | 门洞段的**中心** |
| `width` | `number` | 门洞宽度（沿墙方向量）。当前 `120` = 3 格 |
| `axis` | `'h' \| 'v'` | 开在哪堵墙上 = 人**穿过它的方向**。`'h'` → 沿 y 穿，`'v'` → 沿 x 穿 |
| `toOrder` | `number \| null` | 穿过去到哪个房间。`null` = 墙外（尽头） |

**门段本身不是障碍物**：它表达的是「这里可以出去」。战斗期间关门是 D1 的场景逻辑
（把缺口填上一块可碰撞的矩形），D2 只负责把位置和朝向写对。

| `kind` | 开在哪 | 通向 |
|---|---|---|
| `back` | 主干教室**西墙** (`axis: 'v'`) | 主干上一间（穿过它进西边那段连廊）。**「不回头」规则下玩家一离开就永久关闭** |
| `forward` | 主干教室**东墙** (`axis: 'v'`) | 主干下一间（穿过它进东边那段连廊）。首领**没有** forward |
| `side` | **朝主干的那面墙** (`axis: 'h'`)：宿主那条开在带的上/下墙上、侧室那条同理 | 进侧室（从宿主）/ 回宿主 / 汇回主干下一间（从侧室） |

⚠️ **主干教室的门全部开在东西两面竖直墙上**（v1.0 是开在朝走廊那一面，`axis: 'h'`）。
「主干 ↔ 连廊」两扇门因此是 `axis: 'v'`，**门心比带的中线偏半格**（`y = ±20`）——
因为带高是奇数格、带的中线落在一条格**边界**上，而门洞两端必须落在格**边界**上。
这条偏移是 `layout.ts` 文件头 ④ 推出来的，`config.ts` 里有一条断言守着它
（`mainRoomHeight` 必须是奇数格）；**消费方不需要复算，照 `doors` 里的 `x` / `y` 用即可**。

要点：

- **起点房没有 `back`**（它后面没有房间），**首领没有 `forward`**（它是单局终点）。
- **侧室有两扇 `side` 门，都开在朝主干的那面墙上**：一扇进宿主（入口）、一扇进连廊（出口）。
  两扇门在同一条直线上，正是因为宿主与连廊等高。
- **宿主身上也记着侧室入口那一条**（`toOrder` 指向侧室）。一个门洞、两侧各记一条
  —— 少了宿主那条，宿主里的课桌就会堵在侧室入口前面（净空圈只读本房自己的 `doors`）。
  **按 `toOrder` 去重时别把这两条当成重复。**
- **同一间主干教室的 `forward` 门和它侧室的出口，`toOrder` 是同一个值** ——
  这是「进不进侧室都不改变必经路径」在数据上的样子。

## 4. `Obstacle`

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | `'desk' \| 'chair'` | **它决定的是挡不挡子弹，不是挡不挡路** |
| `rect` | `Rect` | 按格对齐，见 §2.5 |

| 种类 | 挡路 | 挡子弹 | D1 该把它放进哪个分组 |
|---|---|---|---|
| `desk` 课桌 | ✅ | ✅ | 与墙同组（挡玩家、挡怪、挡子弹、挡视线） |
| `chair` 椅子 | ✅ | ❌ | 只挡移动；子弹**穿过去继续飞** |

两种在**寻路网格上完全一样**（都不可走），差异只在子弹碰撞上。生成侧只负责把种类写对。

## 5. 坐标约定（**最容易踩的一条**）

| 东西 | 边界落在哪儿 |
|---|---|
| **房间矩形** | 边界落在**格子的中心**上 |
| **障碍物矩形** | 边界落在**格子的边界**上 |
| `navOrigin` | 格子的**最小角**，且是 `navCellSize` 的整数倍 |

格子中心的坐标是 `navOrigin + cellSize / 2 + k × cellSize`（`k` 为整数）。

为什么房间边界落在**格中心**：房间的边界线就是墙的中线，而墙厚恰好一格 —— 以格中心为中线的
一堵墙**正好封掉那一格**，不多不少。落在格边界上就会「一格中心都盖不住」，于是寻路认为墙两侧
都走得通、物理体照样挡着玩家：**怪穿墙、玩家不穿，两边都不抛异常**。

为什么障碍物边界落在**格边界**：障碍物的尺寸契约是整数格，按格对齐之后，
「看着能挤过去的缝」和「寻路认为能过去的缝」是同一个东西。

> **「可视 = 可走性」是这一整套约定的目的。** 一张摆得下、看着能过的缝，寻路也必须认为能过去。

## 6. `Rect` 的 `x` / `y` 是**中心点**，不是左上角

和测试场的 `WallSpec` 一致 —— D2 吐出来的矩形要能直接喂进 `ArenaBase.configure()`。
四边别自己写 `x - width / 2`，用取数器：

```ts
import { left, right, top, bottom, rectCenter } from '@/domains/procgen/model/rect'
```

一份现成的取数器：`mainRooms(map)` / `sideRooms(map)` / `roomByOrder(map, order)`。
`roomByOrder` **取不到就抛** —— `order` 是连续无洞的，取不到说明数据坏了，
静默返回 `undefined` 只会把错误推迟到某个 `?.` 吞掉的地方。

# 三、尺寸契约（校验器会拒的东西）

| 契约 | 值 | 为什么是这个数 |
|---|---|---|
| 寻路格边长 | **40px** | 地图里带的是 40。格边长必须唯一，否则「同一份可走性判定」只是函数名相同 |
| 墙厚 | **40px = 1 格** | **必须 ≥ 一格**。20px 的墙中心落在格边界上时一格中心都覆盖不到 → 寻路认为墙上有洞 |
| **窄口净宽下限** | **120px** | `minPassageWidth`。窄口 = **连廊净宽（240）与每一扇门宽（120）取小** |
| **主干教室** | **宽度三档 `400` / `520` / `640`，高度统一 `280`** | 只按宽度分档：高度要与连廊等高（见下一条）。**280 必须是奇数格**（`≡ 40 mod 80`） |
| **侧室** | 宽高两维档位：`400×240` / `520×280` / `640×320` | 只有一面墙与主干相邻，宽高都自由取档 |
| **侧室搭接长度** | `k = 侧室宽 − roomGap` ∈ **[半格 + 门宽, 宿主宽]** | 上界：再长就伸到宿主的西墙外面；下界：再短入口门有一半开在宿主外面。生成器按此**过滤档位** |
| **侧室 x 跨度** | `[宿主东边界 − k, 连廊东端]` | = 搭接 + `roomGap`，横跨「宿主的一部分 + 一整段连廊」 |
| **连廊** | 段数 = **主干数 − 1**；高 = `mainRoomHeight`；长 = `roomGap`（200）；两端落在**格中心** | 「教室之间」而不是「贯穿全层」—— 数目与 `between` 一起钉死 |
| **主干 ↔ 连廊的门** | `axis: 'v'`，门心 `y = ±20`（偏半格） | 带高是奇数格 → 带中线是格**边界** → 门心取不到 0，只能偏半格 |
| 门洞宽度 | **120px = 3 格** | **不能取 80**（正好等于肉盾直径、零余量）。还必须**奇数格**，否则两端落在格中心、实际能过 4 格 |
| 门前净空 | **60px 半径** | 障碍物不许长进这个圈，否则门会被课桌堵住 |
| 课桌宽度 | **恒 1 格** | 宽度统一，只有长度变 —— 减少变量的那一条 |
| 课桌长度 | **2—4 格整数**，**只横竖** | |
| 椅子 | **恒 1 格** | |
| **房间/连廊的取景上限** | ≤ **1280×720** | 否则 1:1 的测试场放不下（`test/ArenaBase.ts` 的世界尺寸写死）。最宽的组合是 640 + 两段连廊 + 两侧格边距 = 1120 |
| 障碍物面积占比 | ≤ **0.18** | 按最小档侧室反推的，调大会让小房间变迷宫 |
| 刷怪点 | 每间 **3—6 个**，两两间距 ≥ 80px | |

**校验器接受的是区间而不是等值**：档位表可以改（改 `rooms.json` 即可），
但**每一间房的尺寸都必须命中它那张表的某个档位**，且 `sizeTier` 字段要和反查结果一致。
主干与侧室查的是**两张不同的表** —— 合起来的话，主干教室的高度被改掉也照样合法，
而同一条带里的上下两条墙线正是靠这个高度重合的。

# 四、怎么接

## 1. D3：寻路

```ts
import { buildWalkability } from '@/domains/procgen/walkability'

const isWalkable = buildWalkability(map)        // (x, y) => boolean
new EnemySystem({ /* ... */ nav: { ...navGridOf(map), isWalkable } })
```

**`buildWalkability` 是整个 `procgen/` 唯一该被 D3 调用的可走性入口。**
它内部读的是 `map.navCellSize` 与 `map.navOrigin` —— 不在函数签名里，所以**喂不出不同的格子**。

> ⚠️ 有一点必须说清：`buildWalkability` 判的是「**这一格的中心能不能站**」，
> 与格子的两个方向无关。它不是「从 A 到 B 有没有路」的判定 —— 那是 `FlowField` 的事。
> D2 的职责只到「同一份格子 + 同一份墙和障碍」。

**刷怪位置**用 `room.spawnPoints`。它们的坐标已经落在格中心上，而且**每一个都从门可达** ——
这一条是**由构造保证**的（`gen/spawns.ts` 从门出发做局部 flood fill，只从可达格里选），
不是"校验失败就整张图重来"。

**房间清场后开门**：D2 只给门的位置。事件名（现在议的是 `room_cleared`）归 C1，
D1 定稿后 D2 跟着改名。**在它定稿之前，D3 别把事件名写死在敌人代码里。**

## 2. D1：碰撞、门、战斗

- **墙**：`map.walls` 逐段建碰撞体。**不要自己从 `rooms` 反推** ——
  反推一次就是「同一个事实写两遍」，而这里写错的症状恰好是**没有任何报错**的那种：
  一边推出来的墙少一段，玩家从缝里走出来了，或者怪卡在一个看不见的角里。
- **课桌/椅子**：`room.obstacles`，按 `kind` 分碰撞组（见 §2.4）。
- **门**：`room.doors`。战斗期间封门 = 把门洞那一块填上一块可碰撞的矩形
  （`doorRect(door, wallThickness)` 已经给了这个矩形的算法，`model/rect.ts`）。
  清场后打开 = 撤掉它。**「不回头」= 玩家离开后 `back` 门永久封上，不再打开。**
- **相机取景**：`map.bounds` 是整层包围盒。
  单间房要**并上「门外那一块」**才好看：主干教室并的是相邻的连廊、侧室并的是它的宿主 ——
  `presentation/framing.ts` 的 `roomViewBox(map, cfg, room)` 已经算好了这件事
  （它不 import Phaser，产品侧可以直接用；`presentation/` 里**只有 `floorplan.ts` 碰引擎**）。
  上限：最宽的组合 1120（640 的主干 + 两段连廊 + 两侧格边距），最高 680。

## 3. 别做的事

- ❌ 别在 `client/public/config/` 之外写死血量、速度、伤害、概率（**红线 2**）。
- ❌ 别在游戏核心循环里 `await` 网络（**红线 1**）。
- ❌ 别 import `presentation/floorplan.ts`（**它是 `procgen/` 里唯一 import Phaser 的文件**，
  是给测试场画白箱图用的）。产品代码只用 `model/` `gen/` `walkability.ts` `validate/`。
- ❌ 别改 `map` 对象。字段全是 `readonly`，生成器自己也是**造新对象**而不是就地改。

# 五、配置表 `client/public/config/rooms.json`

| 字段 | 当前值 | 含义 |
|---|---|---|
| `schemaVersion` | `2` | 缺了直接报错 |
| `totalRooms` | `15` | 单局房间总数，恒等 |
| `mainRoomMin` / `mainRoomMax` | `8` / `11` | 主干教室数区间（含两端） |
| `mainWidthTiers` | `[400, 520, 640]` | **主干教室的宽度**档位（px）。每一档取一次随机数，一排里宽度是混着的 |
| `mainRoomHeight` | `280` | **主干教室与连廊的统一高度**（含墙）。必须 ≡ 40 (mod 80)（奇数格），校验器会当场拒绝偶数格 |
| `sideRoomTiers` | `400×240` / `520×280` / `640×320` | **侧室**的宽高两维档位表 |
| `minPassageWidth` | `120` | **窄口净宽下限**（= 连廊净宽与门宽取小）。v1.0 叫 `corridorMinWidth` |
| `roomGap` | `200` | ★ **语义变了**：**连廊沿 x 的长度**（相邻两间主干教室面向彼此的两条边界之间的距离，含两端各半堵墙）。必须取格长的整数倍 |
| `wallThickness` | `40` | 墙厚，必须 ≥ 一格 |
| `doorWidth` / `doorClearance` | `120` / `60` | 门洞宽 / 门前净空半径。门宽必须**奇数格** |
| `deskWidthCells` / `deskLenCells` | `1` / `[2,4]` | 课桌宽（恒 1 格）/ 长度区间 |
| `deskRowsMin` / `deskRowsMax` | `2` / `3` | 成排摆课桌的行数。同一排里桌子之间**留一格当走道** |
| `chairChance` | `0.55` | 每张桌子旁边配一把椅子的概率（贴桌子的上边或下边，随机挑一列） |
| `obstacleDensityMax` | `0.18` | 障碍物面积 ÷ 教室面积上限 |
| `spawnPointsMin` / `Max` / `MinGap` | `3` / `6` / `80` | 刷怪点数量与最小间距 |
| `budgetBase` / `budgetGrowth` | `5` / `1.6` | 威胁预算曲线 |
| `navCellSize` | `40` | 寻路格边长 |

**侧室数不在这里配置** —— 由 `totalRooms − 主干数` 得出。独立配置迟早出现
「主干 + 侧室 ≠ 15」这种自相矛盾的地图。

**威胁预算**：`budget = round_half_up(budgetBase × budgetGrowth ^ t)`，
其中 `t = 主干轴索引 / (主干数 − 1)`，`t ∈ [0, 1]`。**按进度百分比参数化，不按序号** ——
这样 8 间主干的末间和 11 间主干的末间一样强，长局的末尾不会呈指数级强于短局。
