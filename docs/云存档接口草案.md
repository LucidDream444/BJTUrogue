# 云存档接口草案

> 状态：**D4 预留，待 D5 评审，不是已冻结契约**。当前代码尚未请求网络。
>
> D4 负责客户端存档形状、`revision` 与同步状态；D5 负责账号、鉴权、数据库和 HTTP 接口。

## 一、同步范围

同步的是玩家局外进度：

- 已解锁角色；
- 每个角色的技能等级；
- 金币；
- 总局数、胜场、死亡数、最高层数；
- 上次选择的角色和难度。

音量、显示模式默认只保存在设备本地。战斗中的临时状态不进入云档，结算或局外修改后才生成新的 revision。

## 二、离线优先

1. 游戏只同步读写本地 `ProfileStore`，战斗核心永远不 `await` 网络。
2. 本地写入成功后，同步层可以异步上传 `store.snapshot()`。
3. 本地写入失败时显示统一横幅和“重试保存”，不能显示“已同步”。
4. 网络失败不阻塞继续游玩，也不能清空本地档。

## 三、建议的服务端存储

每个玩家一份记录即可，暂不把角色、技能和金币拆表：

```text
user_id
schema_version
revision
payload
updated_at
```

`payload` 就是客户端 `ProfileData` 的 JSON。等出现查询、审计或反作弊需求后再拆表。

## 四、待评审接口

```text
GET  /api/profile/save
PUT  /api/profile/save
```

上传载荷至少包含：

```json
{
  "baseRevision": 17,
  "profile": {
    "schemaVersion": 4,
    "revision": 18
  }
}
```

- 上传成功返回服务器接受的 revision。
- `baseRevision` 落后时返回冲突，不能静默覆盖。
- 重复上传同一个 revision 必须幂等。
- 服务端仍需校验 schemaVersion；客户端迁移逻辑继续负责旧档升级。

## 五、冲突处理

- 只有云端：下载云端档并替换本地缓存。
- 只有本地：首次绑定账号时上传本地档。
- 两边 revision 相同：无操作。
- 云端更新：下载云端档。
- 两边分别产生过新进度：展示“本地进度 / 云端进度”，由玩家选择；金币和升级不能简单取最大值。

## 六、当前客户端切口

- `ProfileStore.snapshot()`：给上传层的深拷贝。
- `ProfileData.revision`：单调递增的存档版本。
- `ProfileStore.subscribe()`：本地修改通知。
- `ProfileStore.lastError` / `save()`：本地写盘状态与重试入口。

不要把云请求塞进同步的 `ProfileStorage` 接口；那会让一次本地保存被迫等待网络，破坏游戏的离线可玩性。
