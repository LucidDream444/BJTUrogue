# 《课后勇者：异次元校园》人员分工方案

> 版本 v2.1 · 制定日期 2026-10-09
> 适用周期：第 4 周 — 第 16 周
> 本文档取代《需求分析与产品设计》§6.3 的分工表。

---

## 一、分工原则：按"设计域"划分，一人一域

**一人拥有一个完整的设计域——从设计到实现到界面，端到端负责。**

不按"策划 / 程序 / 美术 / 测试"的岗位划分。原因有三：

1. **岗位制会让除主程外全员阻塞。** 策划设计完等程序实现，程序实现完等美术画图，美术画完等测试验证——串行链路上任何一环卡住，四个人都在等。
2. **肉鸽的核心是"内容 + 数值 + 系统"的耦合设计**，把设计和实现拆给两个人，等于让两个人各做一半的思考。
3. **一人一域才能度量工作量。** 谁的域推进到什么程度，一眼可见，不会出现"项目经理看起来没产出"这种事。

配套规则：

- 每个域**自己实现自己的界面**，但必须使用统一的 UI 公共控件（由 D4 提供）
- 每个域**自己测试自己的功能**，测试体系由 D3 统一维护
- **服务端从第 5 周独立开工**，全程不被游戏进度阻塞；游戏也全程不被服务端阻塞

---

## 二、五个设计域

| 域 | 设计内容 | 实现内容 |
|---|---|---|
| **D1 战斗核心** | 移动射击手感、命中与受击反馈、武器设计、局内三选一奖励池、难度曲线 | 战斗系统代码、武器与奖励系统 |
| **D2 关卡与地牢生成** | 房间类型与布局规则、路线与关卡节奏、难度爬升、隐藏房间、随机种子 | 生成器算法、可达性校验、配置表 Schema 与校验工具 |
| **D3 敌人与首领** | 敌人类型与威胁分级、AI 行为模式、攻击预警、精英与首领机制 | 敌人 AI 框架对接、行为配置表、敌人表现 |
| **D4 局外成长与存档** | 升级系统 / 技能树、永久解锁规则、资源经济、角色定位与差异化 | 局外系统代码、存档与版本迁移、**全部界面与 UI 规范** |
| **D5 服务端与运维** | 反馈工单流程、匿名身份与账号体系、后台信息架构 | 服务端 API、数据库、鉴权、管理后台、部署与发布 |

**为什么 D4 含存档：** 存档里存的就是解锁进度、升级等级、设置项——它是局外成长的数据形态，不是服务端模块。这一点在 v1.0 里划分错了，导致服务端看起来有两块重复的东西。

**为什么 D4 含全部界面：** 局外成长是界面最密集的域（主菜单、角色升级页、技能树、结算、奖励选择），交给 UI / 美术背景的成员最合理。同时由该域制定 UI 规范与公共控件，另外四个域在此基础上搭建自己域的界面。

## 三、各域详细说明

### D1 战斗核心

**设计输出**
- 移动、射击、闪避的手感参数（加速度、后坐、判定框大小）
- 命中反馈与受击表现规格（顿帧、震屏、闪白、音效触发点）
- 武器表设计：基础武器保底 + 多样性武器
- 局内三选一奖励池设计：奖励类别、强度分级、组合关系
- 难度曲线：入门 / 普通 / 困难的数值差异

**实现输出**
- 战斗系统、命中判定、受击结算、暂停 / 继续
- 武器系统与奖励选择系统
- 战斗 HUD、暂停菜单、操作说明界面

**不负责**：房间生成本身（D2）、敌人行为（D3）、存档（D4）

---

### D2 关卡与地牢生成

**设计输出**
- 房间类型定义（起点、普通战、精英、奖励、商店、首领、隐藏）
- 布局生成规则与连通性约束
- 单局关卡节奏：房间数量、难度爬升曲线、房间类型配比
- 随机种子规则与可复现要求

**实现输出**
- 房间布局生成器
- 地图可达性校验（对应需求文档 R03 风险）
- **配置表 Schema 与校验工具**（C2 契约 owner）
- 小地图界面

**不负责**：敌人具体行为与数值（D3）、战斗结算（D1）

> **提示**：可达性校验是本项目的硬性验收标准（用户故事：随机生成不产生不可通关的房间），必须在迭代 1 内完成并接入自动化测试。

---

### D3 敌人与首领

**设计输出**
- 敌人类型表：近战 / 远程 / 冲锋 / 召唤等，及各自的威胁等级
- 每种敌人的 AI 行为模式与参数（索敌距离、攻击前摇、冷却）
- 攻击预警的表现规格（对应 P2 需求：降低挫败感）
- 精英怪与首领机制设计（分阶段、必杀技、可躲避窗口）
- 敌人数值：血量、伤害、移动速度，按难度分档

**实现输出**
- 敌人 AI 框架对接（框架由 D1 提供接口）
- 敌人行为配置表
- 敌人表现与受击反馈

**横向职责：测试体系 owner**
- 测试用例库、回归清单
- 测试存档（对应需求文档 P1）
- 缺陷跟踪与验证记录
- 各域自测，D3 负责汇总与把关

> **提示**：本域与 D2 都以配置表为工作媒介，两者配合最紧密。

---

### D4 局外成长与存档

**设计输出**
- 升级系统 / 技能树的结构与节点设计
- 永久解锁规则与解锁条件
- 资源经济（金币获取与消耗、升级成本曲线）
- 多角色定位与差异化设计
- **UI 视觉规范**：控件规范、状态规范、版式规范、美术占位规范

**实现输出**
- 局外系统代码（解锁状态机、升级逻辑）
- 存档读写与 `schemaVersion` 迁移机制
- **全部界面**：主菜单、角色升级页、技能树、结算界面、奖励选择界面、设置菜单
- UI 公共控件库与美术 / 音效资源管线

**不负责**：战斗 HUD（D1）、小地图（D2）

---

### D5 服务端与运维

**设计输出**
- 反馈工单流程：提交 → 分类 → 处理 → 验证 → 关闭
- 匿名身份到账号的升级路径
- 管理后台的信息架构，以及三类维护角色的权限边界
  （对应需求文档 §2.1：内容配置人员 / 技术维护人员 / 测试人员）

**实现输出**
- 服务端 API、数据库、鉴权与 RBAC
- 管理后台界面、反馈工单看板
- CI/CD、云环境部署、版本发布与回退机制
- 审计日志

**横向职责：PM 事务**
- 进度跟踪、需求基线、变更记录、文档整合、结题答辩统筹

## 四、域之间的接口

| 接口 | 提供方 | 消费方 | 说明 |
|---|---|---|---|
| **C1 事件总线** | D1 | D3、D4、D5 | 清房 / 受击 / 死亡 / 拾取 / 结算的事件名与载荷 |
| **C2 配置表 Schema** | D2 | D1、D3 | 敌人 / 武器 / 房间 / 奖励的字段定义 |
| **C3 服务端 API 契约** | D5 | D4、D1 | OpenAPI 文档，客户端可对 Mock 开发 |
| **D1 提供敌人 AI 接口** | D1 | D3 | 框架归 D1，行为参数归 D3 |
| **D4 提供 UI 公共控件** | D4 | D1、D2、D3 | 各域界面必须基于公共控件搭建 |
| **D4 提供存档接口** | D4 | D1、D2、D3 | 各域只通过接口读写自己的持久化数据 |

**C1 是最重要的一份契约**：它让 HUD（D1）、敌人表现（D3）、结算界面（D4）、遥测日志（D5）四条线同时挂载到同一个事件流上，一次定义、四处消费。没有它，所有人都要反过来依赖战斗代码。

## 七、服务端推进节奏

服务端独立于游戏迭代推进，节奏如下：

| 阶段 | 周次 | 交付 | 客户端是否依赖 |
|---|---|---|---|
| S0 基建 | W5 | 仓库、CI/CD、云部署、健康检查 | 否 |
| S1 匿名反馈 | W6—7 | 反馈提交 API + 存储 + 附件 | 否 |
| S2 后台最小版 | W8—9 | 硬编码单管理员账号、列表 / 详情 / 状态流转 | 否 |
| S3 遥测 | W10—11 | 事件接收 API（接匿名 ID） | 是（挂遥测接口） |
| S4 账号体系 | W12—13 | 注册 / 登录 / 令牌、匿名 ID 绑定账号 | 是（可选登录） |
| S5 RBAC 与账号管理 | W13—14 | 三角色权限、封禁 / 重置、审计日志 | 否 |
| S6 运维闭环 | W14—15 | 发布记录、版本回退、遥测看板 | 否 |

**"最小 MVP 无账号，但很快需要"的落地方式：**

1. **S2 的管理员登录就是硬编码一个用户名密码。** 最小 MVP 不碰账号体系，但后台已经能用了；S5 再换成真 RBAC。
2. **玩家侧全程可以不用登录。** S1 起反馈链路就靠**匿名 ID**（客户端首次启动生成 UUID 存本地）跑通，服务端能把反馈归属到"某个匿名档案"。
3. **S4 账号上线时做一次绑定**（匿名 ID → 用户 ID），玩家之前的反馈历史自动归到账号下。玩家看到的是"登录后历史还在"，而不是数据清零。
4. **"稳步推进"的判据：每个阶段都不推翻前一个阶段。** S5 是唯一会改 S2 代码的阶段，其余全是纯新增。

技术边界：单体后端（NestJS 或 FastAPI）+ PostgreSQL + Docker Compose；后台前端基于现成 Admin 框架（React-Admin / Ant Design Pro）。**不引入微服务、Redis、消息队列、k8s。**

## 九、协作机制

### 9.1 开发节奏

1. **主干开发 + 短分支。** 分支存活不超过 3 天，每周至少合并一次。
2. **每周固定集成日**（建议周中，非周末）。当天全员合并主干、出一个可运行构建。
3. **每个迭代末必须交付一条可玩构建并现场演示**，不允许"最后一周才集成"。

### 9.2 周会规则

只谈三件事，控制在 30 分钟内：

1. 上周交付能否**现场演示**（不能演示 = 未完成）
2. 本周卡点是什么，需要哪个域配合
3. 接口是否有变更，变更通知到谁

**禁止在周会讨论新需求。** 需求变更一律走变更记录流程，单独评审。

### 9.3 接口变更流程

任何 C1 / C2 / C3 契约的变更，必须：主责方修改契约文档 → 通知全部消费方 → 消费方确认后才可合并。

### 9.4 三条技术红线

1. **游戏核心循环永远不 `await` 网络。** 遥测必须 fire-and-forget，服务端挂掉不影响游戏。
2. **配置数值不写死在代码里**，一律走配置表。
3. **所有本地存档数据带 `schemaVersion` 字段**，为将来迁移留路。

## 十、待确认事项

1. **D3 与 D5 可视技能对调。** 若 D3 更擅长工程与服务端、D5 更擅长内容设计，则两域整体对调，测试体系转由 D4 兼管。两套方案工作量相当。
2. **玩家账号的深度待定。** 本方案按"账号用于身份标识 + 反馈归属 + 统计，进度仍存本地"设计。若决定做云存档，需同步修改《需求分析与产品设计》§1.1 定位与 §3.4 排除项，并评估工作量。
3. **C1 / C2 / C3 的具体字段定义**需在第 4 周内完成，建议由对应主责域各自起草，周内合并评审。

## 十一、与现有文档的差异说明

| 项目 | 原方案（文档 §6.3） | 本方案 | 原因 |
|---|---|---|---|
| 划分依据 | 岗位（策划 / 程序 / 美术 / 测试） | 设计域（一人一域端到端） | 岗位制导致串行阻塞，且无法度量工作量 |
| 项目管理岗 | 纯管理，无代码交付 | 兼 D5 服务端与运维 | 原方案无硬交付物；服务端是其"发布与回退"职责的自然延伸 |
| 系统策划岗 | 策划配置 | D2 生成器 + 配置管线（真正的开发工作） | 随机生成原是主程负担，剥离后主程不再单点 |
| 主程序岗 | 战斗 + AI + 首领 + 随机生成 + 性能 | 仅 D1 战斗核心 | 原范围过载，是项目最大风险 |
| 测试岗 | 纯测试 | D3 敌人与首领 + 测试体系 | 原方案前 6 周无工作对象，属结构性闲置 |
| UI / 美术岗 | UI / 美术 / 前端（仅执行） | D4 局外成长（含设计权）+ UI 规范 | 升级系统设计以界面为主要输出形态，与其能力匹配 |
| 服务端 | 未规划 | D5（覆盖需求文档 UC08—UC11） | 三类维护角色需要落地载体，且需早于游戏启动 |
